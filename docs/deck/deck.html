The problem

Compliance splits twice. Once per chain, once per border.

Every service inside a regulatory perimeter opens with the same question: may I transact with this wallet? There are three ways to answer it today.

Option 1
Rebuild KYC per chain
Vendor minimums, months of integration and data-controller obligations multiply by the number of chains. The user uploads the same document again.
Option 2
Trust a signing server
One key becomes the whole security model, and there is no good answer to a regulator asking why that signature should be believed.
Option 3
Trust a relayer
Trusting the relayer becomes trusting the compliance. The trust moved rather than disappeared.

Crossing a border adds a second problem. "KYC complete" names different work in different places.

JurisdictionWhat it actually requires
KoreaAt least two of: document image, video call, verification on delivery of an access device, use of an existing account. Plus CDD under the FIU act.
EUAMLD customer due diligence, graded against an eIDAS assurance level.
USCIP: collect and verify name, date of birth, address and an identification number.

A single boolean satisfies one of them and gives the others nothing to stand on.

Proofmark05
What we found reading ASCBase

Two security holes that inheritance cannot close.

ASCBase.execute() receives chainKey and blockHeight and passes neither to the handler. We forked it. Verification, queryId and replay protection are untouched.

Finding 1 · chainKey spoofing
CC3 serves Sepolia (chainKey 1) and Ethereum mainnet (3) at the same time. A handler that only checks log.address_ accepts a forged event from a same-address contract on the other chain, and CREATE2 makes claiming that address first straightforward.
require(chainKey == expectedChainKey)
Finding 2 · reordering revives a dead mark
Submission is permissionless and unordered. Send MarkIssued from block 100 after MarkRevoked from block 200 and the mark returns to ACTIVE. The queryIds differ, so replay protection never fires. Both proofs are valid.
lastAppliedHeight[subject]
Both guards are mutation tested. Remove either one and exactly its test fails. test_RejectsProofFromWrongChain  ·  test_StaleIssueCannotResurrectRevokedMark

We also found verifyBatch has no contract-side entry point, so batching runs through multiple logs in one transaction instead. One execute() applies all of them.

Proofmark08
The mechanism

The mark we issue does not pass the production policy we wrote.

That policy asks for document authenticity and bank account verification. Those need institutional agreements we do not have, so those checks did not run, so those bits are not set, and the system reports it.
KR VASP production FAIL
policyId 1 · requireAll 0x10024
Missing: Document authenticity, Bank account
KR pilot PASS
policyId 2 · requireAll 0x190001
Wallet control · Sanctions · Jurisdiction · On-chain exposure
We did not lower the production policy to fit our own mark. An unconnected check is a zero bit, and a zero bit is what lets a consumer reject the mark. Both cards are read live from Creditcoin.
