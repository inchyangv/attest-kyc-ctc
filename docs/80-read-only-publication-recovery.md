# T-23 / T-40 — Verify the original publication without a signing key

2026-09-07. `--resume-publication` can reconcile or rebroadcast the original signed source bytes, but deliberately exits 2 after source recovery: hub materialization is not checked. A delayed relay or publisher interruption should not require a new epoch transaction to obtain complete evidence. The separate `--check` mode checks the current roster and policies, not the journal-to-original-carry linkage.

## Read-only recovery mode

`npx tsx script/publish-epoch.ts --check-publication` uses shell-exported configuration. It does not load dotenv or read `EPOCH_PUBLISHER_PRIVATE_KEY`. Required inputs are the original shared `EPOCH_PUBLICATION_JOURNAL_PATH`, its high-entropy journal key, explicit non-secret `EPOCH_PUBLISHER_ADDRESS`, reviewed source/ASC/Registry addresses and runtime pins, `DEMO_EXPECTED_ISSUER`, source deployment/replay configuration, and `EPOCH_HUB_FROM_BLOCK`. RPC URLs should identify the intended approved networks; repository historical defaults are not approval or migration evidence.

The command holds the journal's existing exclusive local lease, decrypts and validates its scope, and selects the latest non-abandoned entry. It uses a `VoidSigner` only to supply the public address to the existing source observation transport. It never calls publication advancement, signing, broadcast, confirmation persistence or cancellation. The journal ciphertext stays byte-identical. The lock file is created/removed normally, and successful verification writes derived JSON/Markdown evidence: “read-only” describes chain state and journal bytes, not an entirely write-free filesystem operation. A retained crash lock is still a blocker requiring separately authorized owner recovery; this command does not remove it.

The original signed transaction must already have a successful, canonical, sufficiently deep source receipt with the exact stored calldata, epoch event and issuer authorization events. A prior recorded confirmation must agree on transaction/block/hash/status. An unsigned, absent, reverted or insufficiently confirmed source cannot become a success. A transaction accepted before its confirmation was persisted can be observed without adding that confirmation to the journal; later source lifecycle recovery remains a separate operation.

The source roster is rebuilt through the original stored cutoff, with its original root and provenance. The command then applies [exact carry reconciliation](79-exact-epoch-carry.md): acceptance/provenance events, successful hub receipt, original source block/transaction coordinates, processed query and hub block depth/hash. Only that carry is passed to the existing current-epoch, complete frozen-policy, runtime, common-block and proof-verdict checks. It cannot replace an older journal epoch with a newer current epoch. Successful output contains the original source hash and actual matching hub carry, not a new signature or poll timestamp.

`EPOCH_HUB_FROM_BLOCK` is a required inclusive hub-chain scan start at or before the original acceptance. It is not inferred from a source block number, epoch number, latest head or mutable derived record. The existing scan cap is 20,000 blocks through the current head, in 500-block chunks. A floor after the event yields no acceptance; an unavailable/oversized range fails. Failure to find an event establishes only that acceptance was not verified in this supplied window, not that no historical acceptance ever occurred. Archive search and durable authenticated scan-floor planning remain separate work. Do not choose another journal, reduce depth, or fabricate a floor to force success.

Missing carry and early validation failures exit nonzero before rewriting the derived record. Prior evidence files can therefore remain on disk; their presence is not proof the latest invocation succeeded. The usual neutral snippet/complete-record writer applies once final policy verification reaches its output stage. No RPC observation is an atomic cross-chain snapshot, irreversible finality, independently verified native proof or screening-completeness guarantee. The command does not validate current official sanctions bytes before an already-confirmed source receipt; it checks the original committed provenance and current contract freshness, not a new screening run.

## Final source-publication fence

The final cutoff check alone did not cover the later publication transaction. A source reorg can remove the publication while preserving the older roster cutoff and all hub state. The original source receipt was checked before the lengthy hub/replay/policy work, so a successful final verdict could otherwise outlive its source evidence.

Both fresh `--publish` and `--check-publication` now supply a mandatory final source-observation callback whenever they pass carried evidence to `check`. After roster/policy verdicts and the final cutoff check, it re-observes the original signed journal entry using the existing source transport. That repeats transaction/calldata, exact publication/issuer events, canonical source block and configured minimum confirmation depth checks. The new observation must still be successful and match the original transaction hash, block number and block hash. A missing, shallow, replaced or reverted observation fails `PUBLICATION_CONFIRMATION_CHANGED`; RPC/transport errors also fail, without attempting readiness, another signature, transmission or journal persistence. Greater depth and a later observation time are allowed; the original journal confirmation remains immutable.

The successful final record includes `sourcePublicationObservation` with that invocation's transaction/block/hash/status/depth/time. This is observation metadata, not a durable source identity field. Source-only recovery and standalone `--check` strip any prior copy: the latter still checks the current roster rather than recovering the journal/source-carry linkage. The final source callback runs before the existing final hub carry/common-block fences and before successful verdict output or final record/snippet writes. Cross-chain reads remain sequential and cannot guarantee against reorgs after the observation or dishonest RPC consensus. Intermediate fresh-publication source/carry records can already exist; they are not a completed final verification.

Two additional root tests cover unchanged confirmed identity with newer depth/time and refusal of absent/shallow/changed hash/height/transaction/status, unsigned/abandoned/unbound entry and unavailable RPC. They assert identical journal bytes and no readiness/sign/send calls. Record projection and actual source-only resume also test removal of old `sourcePublicationObservation`.

The real CLI integration adds an actual source `evm_revert`, not a fabricated receipt response. It starts read-only verification for the accepted epoch-1 journal; after a real hub non-membership policy call returns, an owned loopback hub proxy restores the source snapshot taken before any epoch publication. The original cutoff block hash remains unchanged, source epoch becomes 0 and its publication receipt disappears, while hub epoch remains 1. The command exits 1 with `PUBLICATION_CONFIRMATION_CHANGED`, never prints final all-verdicts success, preserves the prior JSON/snippet and encrypted journal byte-for-byte, releases its local lease, and sends nothing. The source nonce decreases to the original fixture-issuance nonce because the test reverted the chain; this is not a replacement or new broadcast. The hub worker nonce remains 1. Historical evidence files remain historical, not evidence that this failed invocation passed.
