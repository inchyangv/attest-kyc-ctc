# T-40 — Epoch CLI checks at one hub block

2026-09-07. `script/publish-epoch.ts --check` previously queried latest epoch, provenance, issuer approvals, proof-mode code and three verdicts without a common block. A new epoch, expiry or restriction arriving between calls could mix different states. The record did not identify which hub block its checks described. The later [exact-policy follow-up](75-epoch-policy-check.md) validates the entire frozen demo policy against an explicit expected issuer, and [runtime pins](76-epoch-runtime-pins.md) add exact Source/ASC/Registry image comparisons. Expected booleans or version methods alone are insufficient.

## Implemented boundary

The check now verifies the hub chain and captures one block number, full hash and timestamp before compatibility checks. Registry schema reads, Registry→ASC binding, ASC epoch/authorization versions, ASC→source/chain-key binding, epoch root/provenance/freshness, all roster issuer approvals, registry runtime selector inspection, inclusion verdicts for policies 2/1 and non-inclusion verdict are queried at that same numeric block tag. The source replay helper uses that hub block for its binding checks instead of independently selecting a newer head.

Before writing the record or printing the completed verdict list, the CLI rechecks the source cutoff's number/hash/timestamp and the selected hub block's number/hash/timestamp/network. A mismatch throws and leaves earlier artifacts untouched; old artifacts are historical, not a successful new check. `hubObservation` records chain ID 102031 and the exact block identity. Source-only projection strips this field with the other hub observations so later resume cannot renew it implicitly. Source and hub providers are destroyed on success or error.

`requireRosterV2` accepts an optional block number. The publisher check supplies it; existing callers retain their previous behavior unless they explicitly opt in. This is not a claim that every repository verifier now shares the same observation implementation.

The check remains an RPC-consistency observation at a recent block, not finalized proof, a light client, an authenticated runtime pin, or a promise that a later transaction will pass. Number-tag queries with final hash checks cannot detect every inconsistent or malicious RPC history. The long source replay means the selected block can be older than the head when the command finishes; the recorded timestamp makes that explicit. No maximum observation-age policy is invented here. Source transaction receipt ancestry, public proof-service carry, whole-policy semantic approval and concurrent artifact-writer history remain separate requirements.

## Verification performed

Two new root tests cover exact observation identity/recheck, changed number/hash/timestamp/network rejection, malformed block rejection, and all registry compatibility calls receiving the supplied block tag. Existing epoch-record projection coverage now includes removal of old `hubObservation`.

The existing two-Anvil publication integration adds a separate final branch after its source-only recovery/crash tests. It issues a synthetic sandbox mark to the CLI's demo subject through the real Source, builds the complete source snapshot, publishes epoch 2 using the journal/delivery transport, and reconstructs its record with the actual resume CLI. It relays the actual epoch receipt through an explicitly mocked native verifier into the real ASC, and installs/freeze-checks real production/sandbox policies. This is not a fresh-publication CLI with official AML data.

A loopback RPC proxy then runs the actual `--check` subprocess. It mines a new hub block immediately after the observation block is returned. Every observed `eth_call` and `eth_getCode` still has the original block tag; the command exits 0 with the expected `[true, false, true]` verdicts and records the original canonical block hash/number. Another invocation alters only the final canonical-block response hash. It exits 1 with `EPOCH_HUB_OBSERVATION_CHANGED`, and both JSON and Markdown remain byte-identical to the prior successful observation. The proxy's altered response is a controlled consistency fault, not an actual Anvil reorganization; the earlier publication reorg branch still uses real `evm_revert`.

The integration remains one test, with all earlier source lost-ack/depth/revert/cancel and two actual SIGKILL branches retained. Those earlier source-only branches keep ASC at epoch 0; this new final branch deliberately materializes epoch 2 through the mock-native receipt relay. Test processes use only owned temporary files, local chains and synthetic keys. No public transaction, deployment, official-list refresh or external approval was performed.
