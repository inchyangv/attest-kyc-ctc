# T-23 — Epoch publication journal storage stage

2026-09-07 storage-stage record. **The CLI/transport connection was subsequently implemented; see [current publication recovery](72-epoch-publication-recovery.md).** This document describes the storage boundary and the requirements used for that connection. Its six storage tests alone do not establish network recovery; the later delivery and actual EVM/CLI evidence is separate.

## Storage boundary

`pipeline/epoch-publication-journal.ts` owns one explicit shared path for a dedicated publisher. The caller supplies a high-entropy secret of at least 32 characters and a source-chain/source-contract/publisher scope. It holds an exclusive `.lock` for its whole instance lifetime. Another opener is refused; normal close releases the lock, while a storage-write failure poisons the instance and retains the lock for authorized recovery. There is no expiry, PID takeover, force unlock or deletion/compaction API.

The journal encrypts with AES-256-GCM using a domain-separated SHA-256-derived key; this is not a password-hardening KDF, so human passwords are not suitable secrets. The authenticated context binds the normalized scope. A wrong key/source/chain cannot open existing ciphertext. Scope is frozen, and snapshots/returned entries are copies. Publication is file-fsync → rename → directory-fsync using the existing atomic envelope helper, with private temporary files and mode 0600. A failed post-rename fsync can leave authentic new bytes visible without acknowledging them as durable; the retained lock prevents a subsequent writer from treating that as routine recovery.

An intent stores the exact canonical `publishEpoch` or `publishEpochForIssuers` calldata, source cutoff block number/hash and original creation time. Other functions, trailing calldata and oversized payloads are rejected. Its deterministic ID binds the complete intent and scope. Resume must read the stored intent, not regenerate timestamps or replace its approved plan. The journal authenticates stored bytes, **not issuer approval validity, roster completeness, current source cutoff, account role or fresh AML data**.

Before recording a signed transaction, the journal decodes it and matches signature-derived sender, chain, destination, zero value and exact calldata. It derives hash/nonce from those bytes. Exact replay is idempotent without rewriting. Different signed bytes for an existing entry are refused, including same-nonce fee replacement. Any nonce already present in retained history is refused for a new entry. An unresolved intent blocks a different intent even if it has not been signed. Never-signed plans can be explicitly abandoned with a dated `UNSIGNED_PLAN_CANCELLED` record; signed entries cannot be abandoned. Abandoned plans cannot later be prepared.

Source confirmation binds the original signed hash, block hash/height, success or revert status, positive observation depth and a non-regressing observation timestamp. The first confirmation is immutable; exact repeat does not rewrite. A confirmed success or revert permits a subsequent intent, with old transactions/history retained. **These are structural checks of a trusted caller's observation, not an RPC or canonicality verifier.** No external/user-supplied confirmation should be passed directly to `confirm`. There is no assertion that a receipt will remain canonical after an observation or backup restore.

The journal has an 8 MiB serialized envelope and 1,000-entry bound. It refuses further growth; it does not prune evidence to keep running. Capacity rotation/archiving needs an approved authoritative-history/nonce recovery protocol. Local paths are not global signer identities: all processes using the dedicated key must use the same path, and signing elsewhere bypasses this fence. This is not distributed storage, managed DB/KMS, independent audit storage, guaranteed power-loss durability or an operational recovery approval.

## Integration requirements (implemented scope and residuals in the linked follow-up)

1. Require an explicit journal path/key and dedicated publisher scope before signing. Acquire ownership before deciding the next epoch or nonce. Validate actual chain/runtime/roles, issuer approvals and fresh source snapshot using the existing checks.
2. Freeze the exact calldata/cutoff intent. Populate and sign without broadcasting, then persist raw bytes. No network send if persistence fails or its result is ambiguous.
3. Add an explicit resume path that loads the original intent/transaction before rebuilding a fresh roster or incrementing `lastEpoch`. Query its exact receipt first; when still unresolved, recheck canonical cutoff/authorization conditions before considering identical-byte rebroadcast. Never silently choose a new plan or replacement nonce after lost acknowledgement.
4. Authenticate observed receipt against the stored call, exact source event, current canonical block and required depth; repeat the final canonicality check before allowing the trusted confirmation call. Separate source success/revert from CC3 epoch materialization. Signed source-fork ambiguity requires a hold and approved reconciliation, not automatic replay into a new history.
5. Save/recover the exact roster/publication evidence and preserve its original source/epoch binding; do not merge unrelated `--check` output into a pending send. Awaiting hub carry is not source failure and cannot authorize a new signature for the same publication.
6. Exercise actual CLI with local EVMs and real encrypted files: pre-send interruption, accepted transaction/lost acknowledgement, restart with retained crash lock, exact raw/nonce recovery, canonical revert, same-key concurrent process, stale/forked cutoff and signature-save failure. Normal-path contract tests alone are insufficient.

The storage-only stage did not enable a new production invocation. The linked follow-up makes the journal mandatory and replaces the old direct-send path. T-23 still requires operational, full public proof/carry and independent deployment evidence; this implementation does not close those conditions.

## Current verification

Six root tests use real temporary encrypted files and synthetic EVM signatures. They cover reopen/idempotence/copy isolation/private bytes, exclusive opener and scope/key binding, transaction tampering/replacement refusal, confirmation/history/nonce binding, explicit unsigned cancellation, and an injected directory-fsync failure after rename. The last case independently decrypts the visible ciphertext to confirm the exact signed transaction is present while the writer reports failure and retains its recovery fence. Cleanup closes journal instances before removing only their owned temporary directories.

These tests do not make any network requests, send transactions, verify a source receipt, execute the publisher CLI, or unlock a production journal. Passing them proves only this storage boundary; full deployment/operational evidence is still required.
