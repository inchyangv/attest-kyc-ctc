# T-35 — synthetic inputs in the existing verification flow

2026-09-07. **IN_PROGRESS.** The matching, rejected-document and holder-mismatch presets use the existing wallet → ID → bank → issuance UI and APIs. They are not a separate green-screen simulation of a successful blockchain issuance. No public release, real wallet interaction, institutional request or chain transaction was performed for this change.

## Visitor path

When the status endpoint reports both built-in demo vendors, `/verify` offers three explicitly fictional profiles before wallet connection. A browser canvas draws a small PNG training card headed **SYNTHETIC SAMPLE — NOT AN ID**. It is not a likeness, replica of a government document or a third-party image asset. The form fills the fictional name, date, dummy number, bank account and country values from `pipeline/synthetic-samples.ts`; personal file upload and fixture-field editing are disabled in this built-in demo flow.

Loading a preset makes no wallet, ID, bank, screening or issuance request. The visitor separately accepts the existing notice and signs with a disposable test wallet. Its address is not fictionalized: the notice warns that the address may be published. The ID and bank steps identify themselves as simulated; no real deposit or issuing-authority answer is claimed. A four-digit demo code is shown on the page instead of requiring a bank app.

- **Matching sample:** the actual demo ID and bank adapter rules accept the fictional fields. This does not promise that the final sanctions check, issuance infrastructure, source transaction, relay or current CC3 policy gate will pass.
- **Rejected document:** the fictional name contains the demo adapter's `FAKE` marker. The document response is not authentic; the bank and issuance steps remain locked.
- **Holder mismatch:** the fictional account ends in `99`, exercising the demo bank's mismatch rule and the API's fixed error response. No other account holder's name is shown.

Changing scenarios clears this form's wallet, consent, proofs, pending challenge, result and request reference, and requires a fresh wallet signature. It does **not** cancel or erase a prior server request, revoke an existing mark, release a pending signer or delete recovery records. Existing session-storage request IDs can still be recovered when reconnecting the original wallet. The UI states this distinction before switching.

The sample number and account are fabricated fixtures, **not** officially reserved identity numbers or bank-approved test accounts. They must never be submitted to institutions. The matching profile is not an assertion that its name cannot collide with a future sanctions entry. No allowlist bypass was added to screening.

## Routing and privacy boundaries

The UI adds `syntheticSample=1` to every ID/OCR/continuation form and `syntheticSample: true` to bank start and confirmation. The actual server routes recheck the current demo flag and both adapter identities (`demo:id`, `demo:bank`, each non-live) before a provider operation or bank reservation/consumption. `KYC_DEMO=1` alone is insufficient: a mixed configuration or institutional sandbox/testbed does not qualify. A malformed marker or configuration drift returns a fixed no-store 409 `SYNTHETIC_SAMPLE_UNAVAILABLE`. No sample request automatically falls back to a real provider.

These checks are a routing safeguard, not a classifier proving that all submitted bytes are synthetic. Direct API clients can omit the marker; the general authenticated vendor paths are preserved. Client-side disabled fields do not constitute a universal PII-ingress control. Institutional credentials on a public deployment still require a separately approved access and deployment policy.

The page warns against uploading real identity documents, resident numbers and accounts even before configuration loads. The old resident-number hint “never stored” was removed: demo mode is not a claim of non-retention across browser memory, requests, infrastructure, vendor systems, journal or vault. This change does not modify the existing consent, recovery retention or deletion policy. It makes no legal compliance claim.

Successful non-live results retain their existing vendor provenance and sandbox regime 2. There is no production promotion or change to issuer, policies, sanctions engine or journal prerequisites. Missing recovery-journal configuration still disables issuance. Source and hub deployment incompatibilities are not bypassed.
