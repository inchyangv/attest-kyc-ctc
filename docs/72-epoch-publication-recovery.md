# T-23 — Source epoch publication recovery

2026-09-07. The publisher CLI now uses the [encrypted publication journal](71-epoch-publication-journal.md) through `pipeline/epoch-publication-delivery.ts`. This is local implementation evidence, not a deployment or operational sign-off. T-23 remains `IN_PROGRESS`.

## Commands and ownership

Publication lifecycle commands require `EPOCH_PUBLISHER_PRIVATE_KEY`, its exact derived `EPOCH_PUBLISHER_ADDRESS`, `EPOCH_PUBLICATION_JOURNAL_PATH` and `EPOCH_PUBLICATION_JOURNAL_KEY`. Use a dedicated publisher and one authoritative persistent path shared by every process using that key. The signer/address mismatch is rejected before journal construction or operational RPC work. The journal secret must be independent and high entropy, at least 32 characters. There is no deployer-key fallback. `.env.example` documents these settings; no actual key is supplied here.

The subsequent [exact-policy check](75-epoch-policy-check.md) also requires an independently supplied nonzero `DEMO_EXPECTED_ISSUER` for `--publish` and `--check`. Resume and unsigned cancellation remain source-only operations and do not require or infer this expected policy issuer.

The later [runtime-pin connection](76-epoch-runtime-pins.md) requires reviewed `DEMO_SOURCE_CODEHASH`, `DEMO_ASC_CODEHASH` and `DEMO_REGISTRY_CODEHASH` for publish, resume and check. Cancellation remains local. Three code-image comparisons are now implemented; production approval and linked/native/proxy code identity are not implied.

A subsequent, separate [fresh CLI integration](77-fresh-epoch-cli-integration.md) executes unmodified `--publish` through real synthetic-list parsing, source lost-ack recovery, local mock-native hub carry and final policy checks. It does not establish current official lists or public proof/carry; the recovery tests described below remain distinct.

- `--publish` acquires the journal lease before planning the next epoch. Any unresolved intent requires explicit resume. The most recent completed source transaction is re-observed before a new plan is permitted. Exact intent and signed bytes are saved before broadcast; the existing CC3 wait/check remains a separate stage.
- `--resume-publication` loads the latest non-abandoned intent, observes its exact transaction first and never calculates a new epoch or replaces signed calldata/nonce. A successful source recovery reconstructs the original cutoff roster and writes scoped publication evidence. It prints `CC3 materialization NOT_CHECKED` and exits **2**, not full cross-chain success. Run `--check` separately for its current view checks; this is not a substitute for independently verified public carry evidence.
- `--cancel-unsigned-publication` records explicit cancellation only for a never-signed unresolved plan. It performs no RPC or transaction. Signed plans cannot be cancelled this way. Do not delete the journal, change its path, or rotate to another publisher merely to bypass an unresolved transaction.

`EPOCH_SOURCE_WAIT_SECONDS` is 1–300 (default 30). The loop checks its deadline between transport steps; individual RPC calls have their own timeout, so this is not an absolute whole-command deadline. Source timeout preserves the intent/raw/nonce and returns `PUBLICATION_PENDING_RESUME_REQUIRED`. `EPOCH_RECORD_DIR` optionally redirects local evidence files; the default is `deployments/`. Those JSON records are derived evidence, not the authoritative encrypted transaction journal.

Normal completion/error closes the lease and providers. Ambiguous storage writes poison the journal and retain its lock. A killed process also leaves its lock: there is no TTL takeover or force-unlock command. Recovery requires an authorized owner to establish that the writer is stopped and reconcile durable bytes and chain state. The follow-up below kills actual delivery-harness children and recovers through the actual CLI. It does not establish an approved operational procedure or kill a fresh-publication CLI using official lists.

## Send and observation boundaries

Before signing or identical-byte rebroadcast, the CLI reconstructs the original source cutoff roster, matches its root, checks current official-list provenance/freshness against the original snapshot/version/expiry, and verifies approval coverage. The transport checks source chain, deployed code presence, exact cutoff block hash/number/timestamp and current call simulation, including source roles/signatures. A changed snapshot or expired original plan is a hold, not permission to refresh signed fields. Schema/authorization version checks remain mandatory; these are not reviewed runtime-bytecode pins.

Signing only populates and signs. Journal preparation validates and persists the original transaction before any send. Readiness is checked again after signing, then the exact receipt is observed again in case it appeared meanwhile. A shallow receipt means wait, not rebroadcast. Closed/poisoned journal checks precede signing and the send boundary. A broadcast exception is acceptance ambiguity; recovery observes or sends only the original bytes, never a replacement.

Source confirmation requires matching transaction hash/sender/destination/chain/nonce/calldata/value, a canonical block at the configured depth, and successful-receipt events matching the exact epoch call. There must be exactly one source epoch event and exactly the expected unique issuer authorization events. A reverted receipt is retained as status 0, not publication success. Cutoff and receipt-block canonicality/depth are checked again at the end. A previously recorded confirmation that disappears or changes causes `PUBLICATION_CONFIRMATION_CHANGED`, with no automatic resend or new plan.

These are RPC consistency/depth checks, not a light client or protection against dishonest RPCs or every later deep reorganization. A confirmed source recovery does not need fresh AML data merely to recognize its historical receipt, but it reconstructs the original roster before writing evidence; this does not assert current eligibility. The later [derived-record correction](73-epoch-record-observation-boundary.md) removes implicit evidence merging: source recovery no longer retains old check/propagation fields or old PASS snippets. The resume output deliberately makes no current CC3 verification claim.

## Executed local evidence

Three root delivery tests use real encrypted temporary journals and controlled transports: signature-save directory-fsync failure prevents broadcast; closed/changed readiness and a newly visible shallow receipt prevent inappropriate signing/sending; lost acknowledgement retries only the same signed bytes and a vanished recorded confirmation holds. The six earlier journal storage tests remain separate.

`npm run test:epoch-publication` runs one additional integration test using two actual Anvil chains and actual Source, ASC and Registry contracts. It verifies:

1. Original raw bytes are present in the encrypted journal before the real source broadcast. The wrapper loses the acknowledgement after acceptance; reopening and waiting for depth recovers the same hash with one signature and one source nonce.
2. Concurrent journal ownership and a new pending plan are refused. Missing epoch/issuer events are rejected, and a depth regression on the final head observation remains unconfirmed.
3. The actual `--resume-publication` subprocess reconstructs the source cutoff, writes one correctly scoped temporary record, releases its lease and exits 2 with `NOT_CHECKED`. It does not send another transaction or materialize the hub epoch.
4. Reverting the local source history after recorded confirmation makes actual `--publish` hold with `PUBLICATION_CONFIRMATION_CHANGED`, before a new plan or send.
5. A second dedicated publisher signs while authorized, then loses its role before broadcast. The actual transaction reverts; canonical status 0 is retained. Actual `--cancel-unsigned-publication` subsequently cancels a new never-signed plan without increasing that publisher's nonce.
6. A third dedicated publisher runs the production journal/delivery/transport inside an owned IPC child. The test first kills it with `SIGKILL` after raw persistence but before the send, then restarts the same intent and kills it after actual source acceptance but before journal confirmation. Both deaths preserve the encrypted bytes and exclusive lock. The actual resume CLI refuses each retained lock without modifying ciphertext or increasing the nonce. Only after awaiting the exact child's exit does the test rename its own lock into crash evidence, reopen and verify the original intent/raw/nonce. The second child forbids signing again. After source depth is mined, the actual resume CLI confirms the original transaction with exit 2/CC3 `NOT_CHECKED`; total publisher nonce increases once and ASC remains at epoch 0. Both crash-lock evidence files remain until owned test cleanup.

The recovery branches use synthetic keys, an empty sentinel roster and a fixture readiness callback for direct transport calls. The CLI recovery uses actual historical source replay; it does **not** execute a fresh successful `--publish` with current official AML lists, native proof service or public CC3 carry. ASC stays at epoch 0 during those recovery branches. A later [common-block check branch](74-epoch-common-block-check.md) adds a synthetic mark and local mock-native epoch relay separately. Test subprocesses receive isolated environment/record paths and do not load the workspace's real `.env`. Cleanup removes only owned temporary state and stops only owned Anvil processes. This test is wired into CI and the explicit TypeScript include; it is separate from the root unit-test count.

The crash harness is `test/fixtures/epoch-publication-crash.ts`, requires connected parent IPC and a loopback HTTP source RPC, and derives only a fixed synthetic Anvil key. Its readiness callback is a fixture, not a production bypass flag. The parent checks the child's actual exit signal rather than treating a PID probe or old lock timestamp as proof of exclusive ownership. This models recoverable local process death, not power failure, filesystem loss, another host, or an approved manual unlock procedure. No production lock or journal was touched. The integration remains one test with additional assertions, not three independently counted crash suites.

Remaining release requirements include full fresh-publication CLI/worker/proof/carry evidence, reviewed runtime pins, production storage/KMS and backup recovery, approved publisher crash-owner recovery, authoritative history capacity/rotation, independent audit and approved deployment/operations. The local lease assumes the same dedicated key is not used elsewhere and is not a distributed network-send fence.
