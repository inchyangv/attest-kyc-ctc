# T-39 — Connected local API, storage and consumer integration

2026-09-07, updated 2026-09-08. **IN_PROGRESS.** One integration now connects the built verification page in Chromium, real application routes, issuance journal/vault, source transport, hub contracts and consumer transactions. It uses the repository's currently activated official three-source AML artifact. The injected wallet interface, native cross-chain proof verifier, identity document and bank inputs remain explicit fixtures. This is not a public Creditcoin deployment or a production identity verification result.

## Reproduce

```sh
npm run test:issuance-e2e
```

Install root and web dependencies, Forge/Anvil, Docker and Playwright Chromium first (`npx playwright install chromium`; platform libraries may also be required). The command builds contracts and the web app before starting a pinned Redis 7.4.9 container without network access, host mounts or published ports. `web/tests/issuance-e2e.integration.mts` starts two loopback Anvil processes, a loopback HTTP server, an owned Next frontend process and Chromium. It uses only public development issuer keys, new subject keys and synthetic gas. The activated raw-generation index and baked web index must be byte-identical; the test copies those bytes into its temporary workspace and makes no source fetch. Temporary evidence and the copied AML artifact are removed after the test; the runner stops only its own container/processes. No existing vault or Redis database is used.

The HTTP server dispatches actual wallet, ID, bank, issue, status and onchain route implementations. It does not stub their responses or the issuance pipeline. Non-API page/assets are served from an owned built Next process through the same local origin; API requests never enter that Next process. This exercises the real rendered browser code against the actual route implementations but is not a test of Next's production API transport/middleware or a wallet extension. It does not execute `deploy/verify-demo.mjs`. Built route tracing and driver conformance have separate tests and cannot be inferred from this one. CI runs this integration after installing Chromium, both dependency sets and Foundry; remote CI success has not been observed.

## Connected assertions

Two independently generated wallets complete signed wallet challenges, native PNG validation, demo ID authentication and the one-won-code bank challenge through HTTP. The first uses the direct test client; the second uses Chromium's built verification page, its generated sample PNG and explicit sample/consent/sign/document/bank controls. Neither document is a personal image or government document replica. Both use the same fictional sample persona; the test does not establish unique humans or Sybil resistance. The bank state is explicitly `demo-memory`, not a real bank or distributed bank-state test.

The real v3 index loader and AML engine consume the copied activated artifact. The test requires substantial non-fixture counts in each configured source and pins its snapshot ID in the issuance runtime. The actual issue route computes the credential and salted claims, writes its encrypted Redis journal and configured encrypted file vault, and calls the real EVM transport. Source `issueOnce` receipts are confirmed on the local source chain. Outcomes remain sandbox regime 2: production attribute preview is false and sandbox attribute preview true. A source-confirmed result is not yet a usable roster credential. The same official snapshot ID and its derived list version are then published with the local roster epoch, and each issuance journal outcome must retain that screening snapshot ID before the witness-gated policy can pass.

The test verifies:

- The journal contains the raw signed transaction whose hash equals the API's source transaction hash; the API does not return those signed bytes.
- Redis ciphertext and the encrypted vault file do not contain the fixture name or raw signed transaction in plaintext. This is a targeted storage assertion, not an independent encryption audit.
- The vault is pending after source confirmation, with the actual source hash/chain/contract retained as a receipt observation and membership in the interval-based rescreen due set. A signed-save failure before broadcast has no observation and is excluded. Repeating the original API payload preserves claims, evidence hash and transaction hash, without advancing the issuer's source nonce.
- Combining a fresh wallet flow with another flow's ID/bank proofs fails before a source transaction. A different wallet cannot read the first wallet's journal result.
- Relaying actual source receipt logs materializes the ASC mark. A **newly signed** wallet flow resumes the original request without old ID/bank tokens, preserving claims and transaction hash, without another source transaction. The journal becomes materialized and the vault active with a historical hub acknowledgement. This tests a fresh-token recovery path, not automatic refresh after a 30-minute expiry or browser restart.
- The wallet-authenticated request status endpoint reports source confirmation, CC3 attestation, current Registry policies and asset readiness as separate states. A body that asks this endpoint to `resume` is forced to a read-only lookup. The source-confirmed state and the materialized-but-witnessless state both report asset not ready. After the actual epoch and both membership witnesses are installed, a new status read reports policy 2 PASS and asset readiness without mutating or duplicating issuance.
- The actual onchain HTTP route still reports pilot ineligibility before a current roster witness exists.
- Full source replay starts at the exact source deployment transaction. The issuer signs the new root with EIP-712, the source publishes it, and the hub processes its receipt. Caching current membership witnesses makes both subjects eligible under pilot policy 2 while production policy 1 remains false.
- The consumer mints 100 local units to the first wallet. That same wallet key, which proved HTTP wallet control, signs an actual transfer of 25 units to the second subject. Balances become 75 and 25. The control address fails with the exact `RecipientNotVerified(control, 2)` simulation error.
- After an issuer source revoke is relayed, a real transfer to the revoked recipient mines with status 0. Balances remain 75/25, and the actual onchain route reports pilot ineligibility.

## What is still substituted

Redis executes the actual journal Lua against a real isolated Redis process. Its REST interface is a test-only bridge to `docker exec redis-cli`, not an Upstash-compatible network service, TLS/authentication test, distributed bank store, managed provider conformance result or failover exercise. Non-bridge global fetches in the route process are rejected. EVM RPC endpoints and the HTTP client target only the isolated loopback services.

The integration itself performs no network refresh. It trusts the exact locally activated raw/baked artifact and the T-27 full-GET observation that produced it; byte equality, manifest integrity, freshness and source entry floors are checked again. This does not independently authenticate the publishers, establish legal completeness or keep the artifact fresh after the test. The current local observation is documented in [official snapshot observation](83-official-snapshot-observation.md).

`MockBlockProver` replaces the native inclusion/continuity precompile. Decoder-format wrappers contain actual source logs, but their surrounding proof inputs are synthetic. The real proof builder, query service and relay worker are not part of this execution. Local chain IDs 11155111/102031 are labels on Anvil, not connections to Sepolia/Creditcoin. Local mined finality and timing are not public-chain latency measurements.

The final revoke is an explicit local issuer transaction, not a rescreen/outbox operation. A materialized journal entry records past propagation, not current eligibility; this test does not assert that the vault automatically records that manual revoke. Epoch replacement/expiry and source-to-hub revoke delay have separate [local contract tests](50-local-cross-chain-gate.md).

## Remaining T-39 work

### Response-loss follow-up

Both enrolled wallets now exercise a failure before reaching the successful transfer path. For the first, the real Redis bridge throws only after the signed-payload save commits. The API returns 503 and the source nonce remains unchanged; the persisted entry must already contain the original raw signed transaction. For the second, the local HTTP server destroys the connection after the actual issue route returns a source-confirmed result, before writing any headers/body. Chromium can transparently retry a closed connection, so the harness drops every such original issue reply until the page observes failure. Every dropped outcome must have the same request ID and transaction hash. The page receives no request ID from those responses and the source nonce has increased exactly once.

Both recover using an ID obtained from the **earlier actual wallet-signature response**, not a token decryption, journal lookup or intercepted lost response. A new signed wallet flow reads status and resumes that original ID without ID/bank tokens. The test verifies the original transaction hash, claims/evidence and exactly one consumed source nonce. It also checks that wallet signing alone created no journal entry. The same two subjects then proceed through the existing hub/witness/consumer assertions; no extra test-count claim is made for the fault branches.

Anvil does not mine independently between HTTP calls. The fixture now mines its source head ahead of its wall clock before issuance so `issuedAt` validation during gas estimation is deterministic. This is an explicit local timing control, not a claim that a lagging public head permits immediate issuance. The initial fault test caught an unrelated dependency-diagnostic save instead of a signed-payload save while the local head lagged; assertions on the persisted transaction prevented that from passing as the intended failure. No production timestamp predicate was relaxed.

The page's before-send session storage and reload recovery are now also exercised in this actual-route integration, not only the separate mocked-API test; see the connected browser section below and [the recovery runbook](22-issuance-recovery.md). Actual wallet proof expiry in this combined journey, server/process loss during a lease, managed Redis response semantics, loss of the recovery ID and automatic driver recovery remain distinct cases.

Connect the real proof builder/worker and approved deployment/runtime pins, execute the CLI/browser journey against that isolated complete deployment, verify independent source/hub lineage, and test delayed/expired-token and dropped-response recovery under approved current-source policy. Any public release or issuer-spending run still needs explicit deployment authority and prerequisites. The driver continues to return exit 2 at its incomplete independent-gate boundary. This local integration does not change that exit code or mark the ticket complete.

Initial harness failures were a trailing-slash mismatch on the test Redis URL and a deployment-hash map keyed only by address even though the same development deployer/nonce can repeat an address on two chains. Both were fixed in the harness without relaxing journal validation or source deployment receipt checks.

### Connected browser recovery

`web/tests/browser-issuance-fixture.mts` opens the actual `/verify` page at 390×844. A synthetic event-capable injected provider returns the second subject address; its signing callback signs the actual page-requested challenge bytes with that subject's newly generated EOA key. The key stays in the test process. The actual wallet route verifies the signature and seals its normal tokens/expiry. This is real EOA cryptography behind a mocked provider interface, not extension approval, hardware-wallet or mobile-return coverage.

No API response is supplied by Playwright and no API request is intercepted for replay. Browser traffic is restricted to the owned same-origin server. After the actual ID route decodes the page's generated PNG and the demo bank route generates a code, the test checks the visible code and submits it through the page. The issue request contains the actual opaque ID/bank/wallet proofs produced by those routes.

After the source-confirmed HTTP replies are dropped, the browser shows a fetch error, retains the request ID from its earlier wallet response and has made one application-level issue call. The test reloads the page, confirms no restored `Signed` state, then explicitly loads a sample, consents and signs again. The fresh wallet proof/flow ID differs; the original recovery ID is not replaced. Reload/signature alone sends no issue/status/resume call. New issuance stays disabled because fresh ID/bank proofs have not been acquired.

Clicking `Load original result` calls `POST /api/kyc/status`; `Resume original request` calls the issue route. Both use the new wallet proof and original request ID without old ID/bank proofs. The visible phase and full transaction hash match the recovered outcome. The complete application-level sequence is exactly `issue → status → resume`; both signatures are explicit. Any transport-level retries are counted separately by the dropped reply assertions, not misrepresented as zero wire retries. Claims/evidence/hash and source nonce are checked against the real Redis journal and receipt by the shared assertions. While asset readiness is false and the configured timeout has not elapsed, the page also polls only the read endpoint every five seconds and keeps the last known snapshot across a polling failure.

That same browser-enrolled subject then continues through the existing actual source-log relay, fresh roster/witness checks, receipt of 25 local token units, source revocation and rejected subsequent transfer. Those later chain actions remain test-process transactions, not browser wallet prompts. The first subject still covers signed-save acknowledgement loss through the HTTP client. This extends the existing single integration test; it is not an additional browser suite or public E2E result.

The first connected attempt exposed Chromium's transparent connection retry: dropping only one reply allowed a subsequent reply through, so the expected error was absent. The fixture now holds the response-loss fault across retries and checks their identical transaction identity; no application idempotency check was weakened. Static Next navigation prefetches are explicitly allowed only for known local page paths, and unexpected routes fail the harness. The native verifier, institution, official-source trust, managed Redis and production Next API hosting limits above remain unchanged.
