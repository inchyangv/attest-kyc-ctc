# Sanctions snapshots and freshness (T-27, partial)

Working-tree implementation, updated 2026-09-08 KST. The repository-local CLI pointer and baked web artifact now use the same freshly downloaded official snapshot. No deployed-runtime switch, signed rescreen transaction or alert delivery was performed. T-27 remains `IN_PROGRESS`.

## What the code now enforces

`aml/provenance.ts` owns one rule for raw CLI loading, the v3 web index, and every subsequent screening/list-version request on a provenance-backed engine. All three exact source IDs are required. Provenance **v2** records the configured URL, effective HTTPS **origin/path only**, SHA-256 of the exact effective transport URL, content SHA-256, byte/entry counts, full-GET completion/check time, and an optional raw HTTP Last-Modified header. Query, fragment and URL userinfo are excluded from the public effective URL because official downloads can redirect to temporary signed cloud-storage URLs. Parser version and manifest snapshot ID are separate from the short legacy edition number (first **32 bits**, not eight bytes).

`publishedAt` is deliberately `null`. Neither file mtime, fetch time, index build time nor HTTP Last-Modified is treated as the authority's publication date. Full-GET completion and check time are equal in this version; there is no 304 refresh path. A successful unchanged GET creates a new check manifest while preserving source content hashes/edition numbers.

Canonical UTC timestamps, no future instants, valid chronology, exact parser version, source hashes/counts and exact source sets are mandatory. Freshness is measured from each full-GET completion. The public-screen, issuance, rescreen and epoch paths select `SANCTIONS_{SCREEN,ISSUANCE,RESCREEN,EPOCH}_MAX_AGE_HOURS`; every value must be greater than zero and at most 168, and an exact boundary is accepted while one millisecond over it is rejected. `SANCTIONS_MAX_AGE_HOURS` remains only a compatibility fallback. A rollout plan refuses to form unless all four purpose values are explicit. The example 168/24/24/24-hour values are sandbox engineering defaults, not an approved production risk policy.

The engine copies its input corpus/provenance, binds its purpose-specific age limit, rechecks age before each screen, and includes the full manifest in screening evidence. `evidenceDigest` therefore commits the snapshot alongside the decision evidence. An old engine reference cannot keep screening beyond its age ceiling. A prepared issuance also records the screening snapshot ID and rechecks the current issuance-purpose engine before signing and before every send; a changed or missing snapshot fails without producing new signed bytes. The worker relays the exact source receipt containing that evidence hash, but it cannot independently decode the private evidence. Synthetic and explicitly historical regression engines can omit provenance; they make no freshness claim and are not used by the web/issuance/rescreen runtime entry points.

The FATF June 2026 call-for-action and increased-monitoring statements are a separate `jurisdictionTableId`, with exact official statement URLs, statement date, recheck time, disjoint ISO-2 sets and a bounded `FATF_MAX_AGE_DAYS`. Table edits, future recheck times, stale observations, source drift and overlap fail closed. This records a dated technical observation; the choice to map self-declared nationality/residence to a product decision remains a compliance-policy question.

## Local activation and failure semantics

`fetch-lists.sh` delegates to the TypeScript fetcher. It uses HTTPS-only curl with bounded time/size/retries and requires HTTP 200 plus matching received byte count. Existing gross minimum download sizes remain in place (OFAC/EU >~1 MB, UN >~100 KB). XML is checked for well-formedness, expected source root, forbidden DTD, depth limit, nonempty parsed records, required identifiers/names and duplicate identifiers. The extractor now uses actual XML events, so comments cannot become entries and single-quoted attributes are handled. This is **not** XSD validation or proof that a publisher supplied every legally relevant record.

`snapshot-store.ts` owns an exclusive local `.refresh.lock`. A refresh writes a new UUID generation, fsyncs raw files, builds and reads back a v3 index, writes the manifest, then atomically replaces `data/raw/current.json`. A >20% entry-count drop from an existing generation stops activation for operator review. This is a gross-loss circuit breaker, not a calibrated completeness threshold. All old and failed generations remain available for inspection; no existing flat raw file is overwritten. Crash-left locks must be reconciled with the actual process before manual recovery—there is no expiry-based lock takeover.

The raw loader resolves the pointer once, then hashes and parses the **same bytes** for each source. A missing manifest, mixed file, wrong hash, count mismatch or expired manifest fails. There is no legacy-mtime fallback.

The web cache reads and hashes the compressed artifact on every access and only rebuilds its corpus when content/key changes. It revalidates age even when content is unchanged. A corrupt, absent, unsupported or stale replacement returns an error; the previous cached engine is not used as a fallback for that request. Metadata returned to callers is detached. Public screening success responses carry `Cache-Control: no-store`; status and screening responses expose `sourceSnapshot`. Decompression is capped at 128 MiB, compressed payload validation at 32 MiB; these are artifact limits, not complete HTTP admission/memory controls.

`SANCTIONS_EXPECTED_SNAPSHOT_ID` pins the manifest expected by CLI and web. Scheduled rescreening now requires that pin and stores it in v2 run state, so a run for another snapshot cannot satisfy the monitor. `npm run sanctions:rollout` creates a content-addressed local plan and verifies fresh acknowledgements for web screen, web issuance, rescreen and worker-relay scopes against one snapshot/index/FATF/purpose-policy tuple. Missing or mixed acknowledgements and a changed snapshot without exact v2 rescreen-run evidence produce local findings and a nonzero exit. The gate explicitly reports alert delivery and deployment as not performed; it does not distribute artifacts, install a scheduler or authenticate a remote host by itself.

## Migration and operation

1. Run `bash aml/fetch-lists.sh`. Nonzero exit means no new CLI generation was activated. Inspect the retained diagnostics and repair the actual source failure; do not touch timestamps, omit a source or promote a partial generation.
2. Run `npx tsx aml/eval.ts` against the new current generation. This checks both freshness and the internal regression gate; it does not establish independent AML accuracy.
3. Run `npx tsx aml/build-index.ts`. It rechecks raw provenance and atomically writes the **local** `web/data/sanctions-index.json.gz` v3 artifact. Building never renews source check times.
4. Set all four purpose-specific age limits and use `npm run sanctions:rollout -- plan ...` to bind the index digest, snapshot, FATF table and policy. With separate deployment authority, distribute that exact release and pin to every web/issuer/rescreen/worker scope. Feed authenticated runtime observations to `sanctions:rollout verify`; do not reopen issuance on a mixed fleet.
5. Preview due rescreening using the existing read-only command. A scheduled publishing run additionally requires the exact snapshot pin and writes it to the run state. Follow the rescreen runbook only for an explicitly authorized publishing run and separate CC3 propagation reconciliation. Previously committed negative outbox jobs remain recoverable even if current screening data is unavailable.

Steps 4–5 were **not executed** against any deployed runtime. Fetch and build activated the repository-local CLI generation and baked artifact, not a fleet. A held in-flight screen uses its original still-fresh snapshot, while a prepared issuance from that snapshot is fenced as soon as the active artifact changes. The rollout and rescreen-state gates are local mechanisms; installed scheduling, authenticated observations, alert delivery/acknowledgement and source-to-hub reconciliation still require an approved environment and operators.

Old baked v2 indexes are deliberately rejected by the new web reader. Existing flat XML is accessible only through `loadHistoricalLists` for offline tests, benchmark and `npx tsx aml/eval.ts --historical`; this path is explicitly labelled and never refreshes metadata. CI's normal fetch/build/eval path has no historical fallback. Do not deploy this reader over a v2-only artifact and expect screening to remain available.

## Transport-URL boundary and migration

The first successful isolated download exposed a concrete disclosure path: OFAC and UN redirected to temporary signed storage URLs, and provenance v1 copied the full effective URL into the manifest, index, screening evidence and public snapshot response. The dataset itself is public, but temporary transport signatures/userinfo are not needed in those public outputs. They must not be treated as permanent source locations or evidence of unrestricted cloud access. Do not publish the original diagnostic headers or old candidate manifest.

`publicEffectiveUrl` requires a bounded, well-formed HTTPS URL and stores only its canonical origin/path. Query strings, fragments, username and password are removed before constructing the manifest. `effectiveUrlSha256` commits the original complete transport URL without publishing it; it is not an independently authenticated receipt. Content hashes/counts and exact full-GET times are unchanged. The configured EU URL's fixed public download token remains part of the exact configured source identity; this is distinct from dynamically returned transport credentials. Arbitrary secrets in path segments, raw response headers and infrastructure logs are not generally detected by this change.

All new manifests use provenance v2. Readers reject v1, missing/invalid transport hashes and effective URLs that still contain private components, even if someone recomputes the manifest hash. Warm caches do not fall back to an old accepted engine when the replacement is rejected. The compressed index envelope remains v3 and the XML parser remains `proofmark-lists-2`; the nested provenance version is checked independently. Existing v1-backed artifacts must be replaced with a newly fetched, validated v2 generation and rebuilt index before the new readers are deployed. Do not edit old timestamps, rehash an old candidate as a fresh fetch, mutate historical signed evidence or reuse an old snapshot pin. A full successful refresh can preserve old candidate files while creating a new generation; inspect count-loss/migration requirements before any production switch.

Two added root tests cover simulated signed query/userinfo/fragment removal from manifests, compressed indexes and engine evidence; exact transport hash binding; invalid URL errors without raw input; rehashed unsafe/v1 metadata; and rejected replacement of a warm index. The actual public screen GET/POST route test also checks that private URL markers are absent while the public snapshot ID and origin/path remain correct. These are targeted metadata checks, not a complete PII/infrastructure audit.

## Remaining gates

The local official refresh, v3 artifact, purpose-specific enforcement, prepared-issuance fence, FATF versioning, rollout gate and snapshot-bound rescreen run-state are implemented. Still required are source-specific extraction/validation of legally effective publication times; authenticated durable source receipts beyond local filesystem trust; approved count-loss/schema/completeness and per-purpose age thresholds; installed scheduling and authenticated fleet observations; actual alert delivery/escalation/acknowledgement; authorized rescreen publication and source/hub/gate reconciliation; cross-host rollback/concurrent-publisher prevention; and warm-index polling/refresh cost under approved load. Hashes detect accidental mismatch, **not** a malicious actor who can rewrite both data and manifests. The source endpoints/redirects, local clock, operator-supplied runtime observations and worker's declared release binding remain trust inputs.

XML well-formedness uses pinned `saxes@6.0.0` (ISC; transitive `xmlchars` MIT). Its [official repository](https://github.com/lddubeau/saxes) describes non-validating XML parsing and is archived; lifecycle/replacement ownership belongs in T-54. `npm audit --omit=dev` reported zero known vulnerabilities during the earlier implementation pass, not proof of security. The [European Commission sanctions overview](https://finance.ec.europa.eu/eu-and-world/sanctions-restrictive-measures/overview-sanctions-and-related-resources_en) still directs users to the consolidated financial-sanctions service; the configured official endpoint was used and no mirror was substituted.
